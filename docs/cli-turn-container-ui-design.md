# CLI Turn Container UI 设计方案

## 1. 背景与问题

当前 CLI 交互模式已经具备以下能力：

- 用户提交后立即显示“消息已提交，正在分析并调度任务...”
- 流式展示 LLM 分析状态、工具调用树、Todo 进度、最终结果
- 支持子 Agent 运行态、工具耗时、工具结果摘要等增量刷新

但在真实终端使用中，仍存在明显的用户体验问题：

1. 同一轮问答在运行期间会持续刷新，用户容易把同一块面板的历史残影误认为多条新消息。
2. 当前界面缺少“按用户提问分组”的稳定视觉边界，用户不容易区分：
   - 这是上一轮的最终结果
   - 还是当前轮的运行中状态
3. 历史轮次与当前轮次在视觉上混杂，尤其在长任务、多工具、多轮次的场景下更明显。
4. 虽然已对 `stream_renderer.py` 做过去重与 `transient=True` 收口，但这仍属于“局部止血”，没有从交互模型层面解决“按提问组织信息”的问题。

因此，本次优化不应继续单点修补，而应将 CLI 渲染模型升级为：

- `每次用户提问 = 一个独立 Turn 容器`
- `每个 Turn 只有一个活跃 OpenAkita 视图`
- `旧 Turn 在结束后冻结归档，不再刷新`

这将从根上解决用户误以为“有很多 OpenAkita 窗口信息”的问题。

---

## 2. 目标

### 2.1 主要目标

在不破坏现有 CLI / Agent / Planner / Tool / IM 通道功能的前提下，优化 CLI 界面组织方式，使其具备：

1. 以“用户提问”为粒度组织 UI。
2. 同一轮任务执行过程只存在一个实时刷新的主容器。
3. 历史轮次自动冻结，避免被后续刷新污染。
4. 为后续“折叠/展开历史轮次”提供稳定结构基础。

### 2.2 用户体验目标

优化后用户应能直观理解：

1. 我当前正在看哪一轮提问。
2. 这一轮内部的 LLM 分析、工具调用、Todo、最终结果都属于同一个容器。
3. 上一轮已经结束，不会再被刷新。
4. 如果需要回看历史，只需展开对应轮次，而不是在终端里寻找散落的多个 `OpenAkita` 面板。

### 2.3 技术目标

1. 尽量只改 CLI 渲染层与 CLI 主入口组织层。
2. 不修改核心 Agent 推理协议，不增加对 SSE 事件协议的破坏性要求。
3. 保持现有流式事件源可复用。
4. 为将来接入更强的 TUI（例如折叠、多段摘要、导航）保留扩展位。

---

## 3. 非目标

本次设计不包含以下内容：

1. 不改 Web UI / Desktop Chat 的展示结构。
2. 不改 LLM 推理逻辑、TaskPlanner 逻辑、工具权限系统。
3. 不引入复杂全屏 TUI 框架替换现有 `Rich Live`。
4. 不在本阶段实现终端中的键盘交互式折叠/展开树控件。
5. 不改变消息存储模型，仅优化 CLI 呈现方式。

---

## 3.1 仍需补充的约束

在重新对照真实用户需求后，发现本设计还需要明确以下约束，否则实施时容易偏离“低风险、只优化 UI”的目标：

1. `ERROR` 不能因为历史摘要或折叠而被隐藏。
2. 当前轮的关键失败信息必须优先可见，不能被折叠到摘要之后。
3. 旧轮次容器只能冻结，不能在每次 Live 刷新时整体重绘，否则会再次制造“很多 OpenAkita 窗口”的错觉。
4. 历史 Turn 只允许保存 UI 所需最小摘要，避免长会话造成 CLI 进程内存持续增长。
5. 必须保留一个快速回退开关，确保新 UI 结构出现异常时可以立即退回当前单轮渲染模式。
6. `/clear`、缓存消息重放、`AskUser`、`SecurityConfirm` 这些已有 CLI 特性必须先定义容器行为，再进入开发。

这些约束本质上是本次设计的补充前提，后续所有实现都应遵循。

## 4. 现状分析

## 4.1 当前渲染链

当前 CLI 主流程为：

1. `run_interactive()` 读取用户输入
2. `_process_message(user_input)` 创建 `event_stream`
3. `render_stream()` 用 `Rich Live` 消费同一轮的 SSE 事件
4. 流结束后打印最终面板

当前代码天然已经存在“按用户提问划分处理周期”的边界：

- `main.py` 中每次用户提问只会调用一次 `render_stream()`
- `stream_renderer.py` 内部则负责这一轮期间的所有动态视图更新

这意味着，本次改造不需要动 Agent 主链，只需要把“单轮视图模型”升级为“Turn 容器模型”。

## 4.2 当前问题根因

虽然已经引入 `transient=True` 和内容去重，但用户仍容易误判的根因不是单纯重绘频率，而是：

1. 当前界面没有明确展示“这是第几轮提问”的顶层容器边界。
2. 当前轮结束后虽然面板收口，但历史视觉结构不稳定。
3. 当前渲染状态模型仅服务于“一个活跃 panel 的内容拼接”，没有显式表达“本轮 / 历史轮”的关系。

因此，需要把渲染状态从：

- `single live panel`

升级为：

- `current active turn + archived turns`

## 5. 设计原则

### 5.1 不破坏现有功能

所有改动必须保持以下功能不变：

- 流式响应
- Todo 展示
- 工具调用树
- 错误提醒
- AskUser / SecurityConfirm 中断式交互
- 会话写入
- CLI 命令体系

### 5.2 单轮单容器

一轮用户提问期间，只允许存在一个活跃的 `OpenAkita` 运行视图。

### 5.3 历史冻结

一轮任务结束后，其 UI 容器应立即冻结为静态历史块，不再被未来事件刷新。

### 5.4 结构先于美化

本次优先解决“信息组织混乱”问题，不追求花哨样式。先建立稳定层级，再逐步增强折叠体验。

### 5.5 向后兼容

保持 `render_stream()` 可以继续直接消费当前事件流；新增容器层应该作为“外部包装层”，而不是重写事件协议。

### 5.6 错误优先可见

错误信息是当前 CLI 的重要能力，必须遵守：

1. 当前轮发生 `ERROR` 时，错误摘要必须始终留在当前轮容器的可见区域。
2. 历史失败轮即使进入摘要态，也必须保留失败原因首行。
3. 不允许为了“界面整洁”而把真正错误压入不可见折叠区。

### 5.7 最小状态保留

Turn Container 是视图模型，不是新的长期存储模型。必须限制保留范围：

1. 运行中保留完整当前轮状态。
2. 历史轮优先保留摘要，不保留无限增长的完整中间缓冲。
3. 工具树与 Todo 的完整展开视图仅在当前轮或显式展开时生成。

### 5.8 渐进式替换

第一阶段不应一次性重写整个渲染器，而应采取“双模式可切换”的方式：

1. 先保留当前 `render_stream()` 事件消费主链。
2. 新增 Turn Container 外壳与状态对象。
3. 经真实 CLI 复测稳定后，再逐步把历史摘要和轻交互并入。

## 6. 目标 UI 模型

## 6.1 Turn Container 模型

每次用户提问生成一个 `Turn Container`，结构如下：

```text
┌────────────────────────────────────────────┐
│ Turn #12                                   │
│ 用户: 二维码显示不全，请重新推送到飞书       │
│                                            │
│ OpenAkita                                  │
│ 状态: browser 执行中 | 轮次 6 | 耗时 12:093 │
│                                            │
│ 工具调用树                                 │
│ Todo 进度                                  │
│ 中间状态 / 关键结果 / 错误                  │
│ 最终结果（结束后显示）                     │
└────────────────────────────────────────────┘
```

下一次用户输入后，新增一个新的 `Turn Container`：

```text
┌────────────────────────────────────────────┐
│ Turn #12  已完成                           │
│ 用户: ...                                  │
│ OpenAkita: ...                             │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│ Turn #13  执行中                           │
│ 用户: ...                                  │
│ OpenAkita: ...                             │
└────────────────────────────────────────────┘
```

## 6.2 容器内部分区

每个 Turn Container 内部固定拆成以下区域：

1. `用户问题区`
2. `运行状态区`
3. `执行过程区`
4. `最终结果区`

### 用户问题区

固定显示本轮用户原始输入，作为锚点。

### 运行状态区

显示当前最重要的动态摘要，例如：

- 消息已提交，正在分析并调度任务
- LLM 正在分析请求
- 第 N 轮 | 工具执行中: browser_navigate | 耗时 12:093
- Browser Agent 执行失败 | 当前工具 browser_screenshot | 获取二维码失败

### 执行过程区

显示：

- 工具调用树
- Todo 计划与步骤状态
- 关键链路摘要

### 最终结果区

仅在本轮结束时展示：

- 最终答复
- 关键结果摘要
- 失败说明

## 7. 折叠设计

## 7.1 折叠目标

折叠不是本次必须一次性做完的交互控件，而是要提前在数据结构和渲染布局上预留。

### 初始折叠策略

默认行为：

1. 当前活跃轮次始终展开。
2. 历史已完成轮次默认显示“摘要态”。
3. 历史失败轮次默认显示“半展开态”，保留错误摘要。

### 摘要态展示

历史摘要态只显示：

- Turn 编号
- 用户问题前 1 行
- 最终状态（成功 / 部分失败 / 失败）
- 最终结果摘要前 1-2 行

### 展开态展示

展开时可显示：

- 完整工具调用树
- Todo 列表
- 最终答复全文

## 7.2 本阶段是否实现真实交互折叠

本阶段不建议直接做键盘交互折叠。

原因：

1. 现有 CLI 基于 `Rich + prompt_toolkit`，不是完整 TUI。
2. 真正可交互折叠会显著增加终端状态管理复杂度。
3. 当前用户痛点核心是“刷新像多条消息”，不是“操作折叠按钮”。

因此，本阶段只做：

- 数据结构支持折叠
- 默认历史摘要显示

后续如有需要，再引入：

- `/expand <turn>`
- `/collapse <turn>`
- `/turns`

这类轻交互命令。

---

## 7.3 错误与系统消息的折叠策略

结合真实用户需求，本设计还需明确以下显示规则：

1. 当前轮的 `ERROR` 永不折叠。
2. 工具失败结果默认进入当前轮主视图，不进入仅展开可见区域。
3. 第三方连接噪音、健康检查、后台 INFO 日志不属于 Turn 内容，仍应在日志层治理，而不是并入容器。
4. `AskUser`、`SecurityConfirm` 触发时，当前轮容器应暂停在当前状态，交互完成后继续，不生成新的 Turn。

这样可以避免“为了折叠历史而把关键错误一起藏掉”的副作用。

## 8. 架构设计

## 8.1 渲染层角色分离

将当前 `render_stream()` 的职责拆成两层概念：

### A. Turn Runtime Model

负责维护一轮任务内部状态：

- 用户输入
- 当前状态行
- 工具历史
- Todo 计划
- 子 Agent 运行态
- 最终回复
- 是否已完成

### B. Turn Container Renderer

负责将一轮状态渲染为容器视图：

- 标题
- 状态摘要
- 执行过程区
- 最终结果区

### C. Conversation Timeline Renderer

负责多轮历史展示：

- 当前活跃 Turn
- 已归档 Turn 列表
- 历史摘要

## 8.2 建议新增的数据结构

建议在 CLI 层引入如下轻量数据模型：

```python
class CliTurnViewState(TypedDict):
    turn_id: str
    turn_index: int
    user_input: str
    created_at: float
    status: str
    active: bool
    expanded: bool
    runtime_status: str
    tool_history: list[dict]
    todo_plan: dict | None
    assistant_buffer: list[str]
    final_reply: str
    has_error: bool
    graceful_done: bool
```

以及：

```python
class CliConversationViewState(TypedDict):
    current_turn: CliTurnViewState | None
    archived_turns: list[CliTurnViewState]
```

建议为 `archived_turns` 增加软上限控制，例如：

- 默认仅保留最近 `20` 个历史 Turn 的完整摘要对象
- 更早历史只保留更短的最终摘要或直接不在内存中展开

以避免超长 CLI 会话导致渲染状态持续膨胀。

## 8.3 与当前代码的映射

当前 `stream_renderer.py` 的 `state` 基本可直接迁移为 `CliTurnViewState` 的核心字段：

- `status_line`
- `tool_history`
- `todo_plan`
- `sub_agent_runtime`
- `graceful_done`
- `has_error`

因此本次改造不是推倒重来，而是：

- 将现有 `state` 从“匿名 dict”提升为“单轮视图对象”
- 在 `main.py` 增加历史 turn 管理器

## 9. 渲染策略

## 9.1 当前轮

当前轮仍采用 `Rich Live` 原地刷新，但只刷新当前轮容器内部。

## 9.2 历史轮

历史轮在当前轮完成时，转为静态 `Panel`，不再进入 `Live.update()`。

关键点：

1. 运行中只刷新当前轮容器。
2. 历史轮不得在每次事件时重新参与整页重绘。
3. 当前轮结束后，只允许追加一次静态归档输出，不能反复重复打印。

## 9.3 结束时的行为

当前轮结束后：

1. 将当前 `CliTurnViewState` 标记为 `active=False`
2. 写入 `archived_turns`
3. 渲染为最终静态卡片
4. 等待下一轮输入时创建新的 `current_turn`

这样可以从根本上避免“后一轮把前一轮内容又刷新一遍”。

## 10. 兼容性评估

## 10.1 对系统功能的兼容性

### 完全兼容

以下模块理论上无需改动业务逻辑：

- `core/agent.py`
- `core/task_planner.py`
- `agents/orchestrator.py`
- `tools/handlers/*`
- `events.py`

原因：

本次只重构 CLI 的呈现方式，不改变事件源与业务执行链。

### 轻度影响

以下模块会受影响，但属于展示层范围：

- `src/openakita/cli/stream_renderer.py`
- `src/openakita/main.py`

### 潜在受影响的测试

- `tests/unit/test_stream_renderer_todo.py`
- 可能新增 `test_cli_turn_container.py`

## 10.2 对会话存储的兼容性

不改变现有 session / message 持久化格式。

如需保存“历史容器的折叠状态”，建议只作为 CLI 运行时状态，不进入长期存储。

同时补充：

1. `/clear` 后应重置 Turn 计数与当前历史容器缓存。
2. 通过 `early_input_queue` 重放的消息，每条缓存消息仍应拥有独立 Turn 容器。
3. `sessions` / `session` 命令仍只管理会话，不需要感知 Turn Container 持久化。

## 10.3 对 SSE 事件协议的兼容性

不要求变更现有事件类型。

最多允许新增可选字段：

- `turn_id`
- `turn_index`

但第一阶段甚至可以不新增，直接在 CLI 层生成。

## 12. 破坏性评估

## 12.1 低破坏性结论

本方案整体属于低破坏性改造。

原因：

1. 不改事件协议主语义
2. 不改核心执行链
3. 不改持久化协议
4. 主要变更局限于 CLI 渲染层

## 12.2 主要风险

### 风险 1：AskUser / SecurityConfirm 的 Live 中断恢复

当前 `render_stream()` 中遇到这类事件会 `live.stop()` 再恢复。
如果 turn 容器结构复杂化，恢复位置需要重新校验。

### 风险 2：历史容器数量过多导致终端输出过长

如果每轮都完整展开，长会话仍会很高。
因此必须在阶段二配合“历史摘要态”。

### 风险 3：测试样例与真实终端行为不完全一致

Rich `Live` 在真实 TTY 与 record console 下表现存在差异。
所以必须增加真实 CLI 回归验证，而不能只依赖单测。

### 风险 4：阶段一改动过大导致定位困难

如果在第一轮实现中同时引入：

- Turn 容器
- 历史摘要
- 折叠状态
- 新命令

那么一旦出现问题，很难快速判断是容器边界、Live 重绘、历史归档还是摘要逻辑导致。

因此必须严格限制第一阶段范围，只做“当前轮一个容器 + 历史冻结”。

### 风险 5：无回退能力

若缺少开关，一旦新容器视图在某些终端环境下出现排版异常，当前 CLI 体验会整体回退。

因此建议增加配置或运行时常量，例如：

- `CLI_TURN_CONTAINER_ENABLED=true`

用于快速切回旧渲染模式。

---

## 13. 用户体验收益

优化完成后，用户将获得以下体验收益：

1. 明确知道每一块 `OpenAkita` 信息属于哪一次提问。
2. 不再把同一轮运行中的刷新误认成多条新消息。
3. 长任务可持续观察当前进度，但不会污染已完成历史。
4. 历史轮次可摘要保留，回看成本更低。
5. 后续可逐步增加折叠、过滤、只看失败轮次等增强能力。

## 14. 推荐实施策略

建议分三阶段实施：

### 阶段一：建立 Turn 容器骨架

目标：

- 一次提问一个容器
- 仅当前容器刷新
- 历史容器冻结

### 阶段二：历史摘要与默认折叠

目标：

- 历史轮次默认摘要化
- 当前轮保持展开
- 失败轮显示错误摘要

### 阶段三：轻交互增强

目标：

- 增加 `/turns`
- 增加 `/expand <n>`、`/collapse <n>`
- 视需要支持“仅看当前轮 / 仅看失败轮”

---

## 14.1 重新校准后的最小落地范围

结合“避免一次性大规模实现”的要求，建议将第一轮开发范围进一步收缩为：

### 第一轮只做

1. 为每次用户提问分配 `turn_id / turn_index`
2. 当前轮包裹成单个顶层 Turn 容器
3. 当前轮结束后冻结成静态历史块
4. 下一轮开始时不再刷新前一轮
5. 保持现有工具树 / Todo / 错误显示不变
6. 增加容器模式开关，支持快速回退

### 第一轮明确不做

1. 历史摘要裁剪
2. 折叠/展开命令
3. 历史容器可交互查看
4. 复杂的多段布局美化

### 第二轮再做

1. 历史摘要态
2. 失败轮半展开
3. 历史数量上限

### 第三轮再做

1. `/turns`
2. `/expand`
3. `/collapse`

这样才能保证每一轮改动都足够小、可验证、可回退。

---

## 15. 最终建议

推荐采用 `Turn Container + 历史冻结 + 历史摘要` 方案，而不是仅仅在当前 `OpenAkita` 面板外再套一个更大的框。

理由：

1. 这是结构性解决方案，不是样式级遮盖。
2. 对现有系统兼容性最好。
3. 改动集中在 CLI 展示层，风险可控。
4. 能直接支撑后续折叠能力。

本次开发的核心原则应保持为：

> 在不破坏现有系统功能的前提下，只优化 CLI 信息组织方式，增强用户对“当前轮 / 历史轮 / 运行中 / 已完成”的感知能力。
