# CLI Turn Container UI 开发计划

## 1. 开发目标

基于 `docs/cli-turn-container-ui-design.md`，在不破坏现有系统功能的前提下，逐步完成 CLI 界面优化：

1. 每次用户提问形成一个独立 Turn 容器
2. 当前轮实时刷新
3. 历史轮冻结归档
4. 历史轮默认摘要显示
5. 保持现有 Todo / 工具树 / 错误提醒 / AskUser / SecurityConfirm 能力不退化

---

## 2. 总体策略

采用“小步快跑 + 每步可回退”的实施方式：

1. 先建立容器边界，不动复杂交互
2. 再补历史摘要
3. 最后再做轻交互增强

每一阶段都要求：

- 单测通过
- 诊断无新增错误
- 至少一次真实 CLI 复测

并额外增加一条硬约束：

- 每一阶段都必须保留可回退开关，避免新 UI 模式一次性替换旧模式

---

## 3. 分阶段计划

## 阶段 A：Turn 容器骨架

### 目标

让“一次提问”成为一个稳定的顶层 UI 容器。

### 改动范围

- `src/openakita/main.py`
- `src/openakita/cli/stream_renderer.py`
- 新增或扩展 CLI 渲染辅助结构

### 主要任务

1. 在 `main.py` 为每次 `_process_message()` 分配 `turn_id / turn_index`
2. 在 `render_stream()` 层引入单轮 `TurnViewState`
3. 将最终输出改为“Turn 容器”而不是裸 `OpenAkita` 面板
4. 保证同一轮只存在一个活跃刷新区域
5. 当前轮结束后转成静态历史块
6. 增加 `CLI_TURN_CONTAINER_ENABLED` 之类的回退开关

### 交付标准

1. 一次提问只生成一块最终历史容器
2. 下一次提问开始时，上一次容器不再刷新
3. Todo / 工具树 / 最终答复仍正常显示

### 验证点

1. 普通问答
2. 带 Todo 的编排任务
3. 带工具树的长任务
4. 中途出现错误的任务
5. `/clear` 后 Turn 计数与历史容器是否正确重置
6. `early_input_queue` 重放消息是否每条都生成独立容器
7. `AskUser / SecurityConfirm` 后是否仍回到同一 Turn

---

## 阶段 B：历史摘要与默认折叠

### 目标

解决长会话滚动过长的问题。

### 主要任务

1. 为历史 Turn 引入摘要态渲染
2. 当前轮默认展开
3. 历史成功轮默认摘要显示
4. 历史失败轮显示错误摘要
5. 摘要内容至少包含：
   - Turn 编号
   - 用户问题摘要
   - 最终状态
   - 最终结果摘要
6. 为历史 Turn 增加数量上限与最小保留策略

### 交付标准

1. 长会话中历史区不会充满大段工具树与 Todo
2. 用户仍能快速知道每轮是否成功
3. 当前轮查看体验不受影响

### 验证点

1. 连续多轮提问
2. 既有成功轮也有失败轮
3. Todo 复杂任务后的历史摘要是否清晰

---

## 阶段 C：轻交互增强

### 目标

在不引入复杂 TUI 的前提下，提供最小交互增强。

### 候选功能

1. `/turns`：列出历史轮次摘要
2. `/expand <n>`：展开指定轮次
3. `/collapse <n>`：折叠指定轮次
4. `/turn <n>`：查看指定轮次完整详情

### 说明

这一阶段不是本轮 UI 收口的必需项，可放在后续执行。

---

## 3.1 进一步拆细后的推荐执行顺序

为避免第一轮实现过大，建议将阶段 A 再拆成两个很小的子阶段：

### 阶段 A1：容器外壳接入

只做：

1. `turn_id / turn_index`
2. 当前轮顶层容器
3. 旧轮冻结
4. 回退开关

不做：

1. 历史摘要
2. 折叠
3. 历史数量控制

### 阶段 A2：容器内区块稳定

只做：

1. 将用户问题区、运行状态区、执行过程区、最终结果区固定下来
2. 校准 AskUser / SecurityConfirm / ERROR 在容器内的位置
3. 验证不再重复打印窗口

说明：

只有 A1 真实复测稳定后，才进入 A2。这样每一步都足够小。

---

## 4. 模块任务拆解

## 4.1 `src/openakita/main.py`

### 任务

1. 为每次用户输入维护 `turn_index`
2. 为 `render_stream()` 传入当前 turn 的上下文
3. 在流结束后将本轮结果写回会话，同时保留 UI 归档信息

### 风险

低风险，主要是入口参数扩展。

## 4.2 `src/openakita/cli/stream_renderer.py`

### 任务

1. 抽离 `TurnViewState`
2. 构建 `Turn Container` 顶层渲染函数
3. 区分当前轮渲染与历史轮渲染
4. 增加摘要态构建函数
5. 复用现有：
   - Todo markdown
   - 工具调用树 markdown
   - 动态状态行

### 风险

中风险，这是本次核心改动点。

## 4.3 单测层

### 任务

1. 扩展 `test_stream_renderer_todo.py`
2. 必要时新增：
   - `test_cli_turn_container.py`
3. 覆盖：
   - 单轮实时刷新
   - 历史冻结
   - 历史摘要
   - AskUser / SecurityConfirm 中断恢复

---

## 5. 兼容性与回归要求

## 5.1 必须保持兼容的功能

1. `render_stream()` 可继续消费现有 SSE 事件
2. Todo 仍然按原逻辑更新
3. 工具树仍能实时显示
4. `ERROR` 仍能直接提示给用户
5. `AskUser` / `SecurityConfirm` 仍能中断并恢复
6. `Lark` 等第三方错误日志不因为容器改造而被吞掉

## 5.2 不允许退化的体验

1. 提交后即时反馈不能丢
2. LLM 运行状态可见性不能丢
3. 工具结果“已完成 / 失败 / 原因”不能丢
4. 毫秒级耗时和轮次树不能丢
5. 当前轮关键错误不能被历史摘要或折叠机制隐藏

---

## 6. 风险控制策略

## 风险 1：历史容器与当前容器状态串写

### 控制措施

1. 当前轮使用独立状态对象
2. 结束后深拷贝归档
3. 历史容器只读，不再接收事件

## 风险 2：结束时仍重复打印

### 控制措施

1. 严格限制“最终 `console.print`”只发生一次
2. 当前轮与归档轮分别走不同渲染路径

## 风险 3：长会话输出过大

### 控制措施

1. 阶段 B 引入摘要态
2. 默认仅当前轮完全展开

## 风险 4：没有快速回退路径

### 控制措施

1. 新老渲染模式并存一段时间
2. 使用配置开关控制 Turn Container 是否启用
3. 真实复测若发现兼容问题，优先切回旧模式而不是在线热修复杂布局

---

## 7. 测试计划

## 7.1 单元测试

至少覆盖：

1. 单轮容器渲染
2. 两轮提问时历史冻结
3. 历史摘要渲染
4. 工具树与 Todo 在容器内同时展示
5. 错误轮摘要
6. `/clear` 后历史重置
7. 缓存消息重放生成独立 Turn

## 7.2 真实 CLI 回归测试

至少执行以下场景：

1. 普通问答
2. 二维码检查与重推
3. 工具失败场景
4. AskUser / SecurityConfirm 场景
5. 连续多轮问答场景

## 7.3 验收标准

1. 用户不会再把刷新中的同一轮误认为多条独立 `OpenAkita` 消息
2. 长任务中，当前轮与历史轮边界清楚
3. 历史轮不会在新提问过程中被重新刷新

---

## 8. 实施顺序

推荐按以下顺序执行：

1. 阶段 A1：容器外壳接入
2. 阶段 A1 单测
3. 阶段 A1 真实 CLI 复测
4. 阶段 A2：容器内区块稳定
5. 阶段 A2 单测
6. 阶段 A2 真实 CLI 复测
7. 阶段 B：历史摘要
8. 阶段 B 单测
9. 阶段 B 真实 CLI 复测
10. 根据效果决定是否进入阶段 C

---

## 9. 本轮建议执行范围

为了控制风险，本轮建议只做：

1. 阶段 A1：容器外壳接入
2. 阶段 A2：容器内区块稳定

暂不做：

1. 交互式折叠命令
2. 全屏 TUI 改造
3. 会话级持久化折叠状态
4. 阶段 B 的历史摘要与数量控制

---

## 10. 最终判断

该方案符合以下前提：

1. 以不破坏现系统功能为大前提
2. 本次聚焦优化 UI 显示问题
3. 通过结构性重组增强用户体验
4. 风险集中在 CLI 层，整体可控

因此，建议下一步直接按本计划进入：

- `阶段 A1：容器外壳接入`
